If you've tried running multiple coding agents on a Wasp project at the same time, you've probably hit a wall.
Two worktrees, two agents, and only one of them can actually start the app. Sound familiar? Wasp 0.26 fixes this. Each worktree now gets its own ports automatically, so `wasp start` and `wasp start db` work side by side across as many worktrees as you need.

We also improved what happens when two Wasp commands collide in the same project. Instead of a cryptic failure, you now get a clear error that tells you exactly which process is in the way.

Nothing about your day-to-day workflow changes. No breaking changes. No migration. It just works.

Read on for the details, or jump straight to [How to use it](#how-to-use-it) if you just want the commands.

## TL;DR

- `wasp start` and `wasp start db` now pick the first free port instead of insisting on `3000`, `3001`, and `5432`.
- Wasp handles the plumbing between the client, server, and database, so they always find each other, even across worktrees.
- Running conflicting Wasp commands in the same project now fails with a clear error and the PID of the process holding the lock.
- New `--client-port` and `--server-port` flags let you pin the ports when you need to.

## The workflow we're supporting

Agent orchestrators like [Herdr](https://github.com/herdrdev/herdr), [Workmux](https://github.com/raine/workmux), and [Conductor](https://www.conductor.build/) let you work on several features in parallel. The pattern is roughly the same across all of them:

1. The orchestrator creates a [Git worktree](https://git-scm.com/docs/git-worktree) for each feature and hands it to an agent. The agent edits code, runs commands, and tests its work inside that worktree.
2. You check in as the agents make progress. The orchestrator pings you when one of them needs a decision, and you iterate until the feature is ready.
3. You merge the branch into `main` and delete the worktree.

It's a genuinely nice way to work. The problem was that older versions of Wasp didn't play along. The bottleneck wasn't the agents, it was Wasp. Two things got in the way, and 0.26 addresses both.

## What was the problem?

The two issues show up at different levels: one inside a single worktree, and one across worktrees. Let's take them in order.

### Process conflicts within a worktree

{/* TODO: maybe SQL state */}

It's surprisingly easy to run `wasp build` while `wasp start` is already running in the same project. One terminal has the dev server up, another one gets a build command, and nobody notices until something breaks. Humans do this occasionally. Agents do it a lot, and this is what gets most people.

Both commands operate on the same generated files. Older versions of Wasp didn't guard against this, so the second command would either quietly corrupt something in the background or fail with an error that pointed nowhere near the real cause. The silent version is especially nasty: nothing complains, and you only find out when the app starts behaving strangely twenty minutes later. Either way, whoever was reading the output, you or the agent, ended up on a wild goose chase.

Wasp 0.26 still allows only one of these commands to run per project at a time. What's new is that the second one tells you exactly what's happening and who's holding the lock:

```
$ wasp build
❌ --- [Error] Wasp project is already in use: ------------------------------------

Another Wasp command (PID 3011345) is already running for this project. Stop it before running this command.
```

This isn't just a friendlier error message — it's an actionable one. For a person, that's a one-line fix instead of a debugging session. For an agent, it's the difference between recovering on its own and asking you what went wrong.

### Port conflicts across worktrees

This one is more fundamental, and it's the one that actually blocks the workflow. A worktree gives an agent its own copy of the code and its own directory to run commands in, which covers most of what it needs to work independently. But not everything is scoped to a worktree. The problem isn't that worktrees don't isolate enough — it's that ports aren't the kind of thing a worktree can isolate. They belong to the whole machine.

Running a Wasp app in development with Wasp's dev database involves two commands and three processes:

- `wasp start db` starts a Postgres database in a Docker container, exposes a port on your machine, and gives you a connection URL.
- `wasp start` starts the Node server and the Vite dev server for the client.

Those three processes need to find each other: the client needs the server's URL, the server needs the database's URL, and so on. Older versions of Wasp had no way for a process to tell the others which port it was on, so the ports had to be fixed in advance: `5432` for the database, `3000` for the client, `3001` for the server.

If you're working on one thing at a time, that's fine. You never notice.

Add a second worktree and it stops being fine. Here's where it bites: both worktrees want the same three ports, and there's only one `3000` on your machine. In practice, no two agents could have their dev servers running at the same time, which rules out a lot of the testing you'd want an agent to do on its own.

## How we fixed it

The core idea is simple: each process takes the first free port instead of insisting on a specific one.

When two agents run `wasp start db`:

- The first one gets a database on `localhost:5432`.
- The second one gets a database on `localhost:5433`.

When they run `wasp start`:

- The first one gets the client on `localhost:3000` and the server on `localhost:3001`.
- The second one gets the client on `localhost:3002` and the server on `localhost:3003`.

Simple to describe, less simple to build. And here's the kicker: the hard part isn't picking a port — it's making sure every other process finds out which port was picked, including a database that was started ten minutes ago in a different terminal. Wasp now handles that itself: it passes the client and server their URLs when it starts them, and it asks Docker where this project's database container is running rather than assuming `localhost:5432`.

There's a long tail of edge cases behind that sentence, but none of them matter for using the feature, so we'll spare you the details.

## How to use it

Run the same commands you've always run:

```bash
# Starts the client and the server on the first two free ports,
# starting from 3000 and counting up.
wasp start

# Starts the dev database on the first free port,
# starting from 5432 and counting up.
wasp start db
```

One thing worth keeping in mind: your app won't always be on the same ports anymore. If `3000` is taken, the client moves to the next free port and the server follows. Wasp prints the URLs when it starts, so check them rather than assuming.

If you'd rather pick the ports yourself, you can. The same flags work for both `wasp start` and `wasp build start`:

```bash
wasp start --client-port 4000 --server-port 5000
wasp build start --client-port 4000 --server-port 5000
```

Explicit ports are treated as a requirement, not a hint. If one of them is taken, Wasp fails instead of quietly moving elsewhere. This might feel harsh at first, but it's deliberate. That's not stubbornness, it's predictability: if you asked for a specific port, you probably have a reason, and silently ending up on a different one would break whatever that reason was. Free the port, pick another, or drop the flag.

## Try it out

Parallel worktree support is live in Wasp 0.26. If you're not on it yet, update your Wasp CLI:

```bash
npm i -g @wasp.sh/wasp-cli
```

One heads-up: since Wasp now manages the ports and URLs in development, setting them yourself (for example, `server.port` in `vite.config.ts` or `PORT` in `.env.server`) is now an error. The [migration guide](/docs/migration-guide) covers everything that changed and how to update your project.

Try it with your agents and let us know how it goes on [Discord](https://discord.gg/rzdnErX). And if something else is still getting in their way, we'd genuinely like to hear about it. That's exactly how this release came about.
