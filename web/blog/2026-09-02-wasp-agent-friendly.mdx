## What's new?

Wasp 0.26 improves support for agent orchestrators and Git worktrees.

If you're the kind of person to use a web framwork in Beta, you almost certainly know what those things are.
But just in case you don't:
- An **agent orchestrator** is a tool for coordinating agents. It helps you assign tasks to agents and keep track of their work, without juggling thirteen terminal windows and losing your mind. Examples of popular agent orchestrators are [Herdr](https://github.com/herdrdev/herdr), [Workmux](https://github.com/raine/workmux), and [Conductor](https://www.conductor.build/).
- **[Git worktrees](https://git-scm.com/docs/git-worktree)** are a Git feature that lets you checkout multiple branches of a Git project at the same time, each one in its own isolated directory.

Using these two tools in tandem creates a perfect setup for a team of agents working on several features at the same time.
Worktrees keep each agent in its own lane, and the orchestrator lets you easily oversee the whole ordeal.

A typical workflow goes something like this:
- The orchestrator gives each agent an isolated Git worktree. Inside it, the agent can edit code, run tools, test the feature, and do whatever else is necessary to get the job done.
- The agents get to work, and you all do some back-and-forth. The orchestrator lets you know every time an agent needs your input, and you iterate until the feature is done.
- When a feature is done, you review the diff in its worktree. If all is well, you use the orchestrator to merge it into `main` and delete the worktree.

It's a great way to get things done, but previous versions of Wasp had a few problems that made such workflows impractical.
It wasn't impossible to set it up, but, since you'd have to fight Wasp every step of the way, it almost defeated the whole purpose.

Wasp 0.26.0 finally solves all these problems. Multiple agents can now work on a Wasp project without getting in each other's way, and without you having to do anything special.

We're about to get into the specifics of what makes Wasp 0.26.0 agent-friendly.
We'll explain the problems Wasp used to have and how the new version solves them.
If you don't care about any of this and just want to get some work done, skip over to [How to use this?](#how-to-use-this)

## What were the problems anyway?

Wasp's intolerance of worktres and orchestrators came down to:
- Process conflicts between CLI commands in the same worktrees.
- Port conflicts between CLI commands in different worktrees.

Even though you could set everything up, common failures caused by these issues prevented agents from getting any work done.

To make things worse, when an agent ran into these problems, it wouldn't just realize what's happening and stop.
Wasp's error messages would act as a red herring and keep the agent wasting time and tokens until the user realized what's happening and intervened.

Let's now look at both problems in more detail.

### Process conflicts inside a worktree

Wasp has a bunch of CLI commands (`wasp start`, `wasp build`, `wasp install`...).
Some of those commands can't run at the same time.
For example, `wasp build` and `wasp start` both watch the same source files and write to the same place, so running them simultaneously creates chaos.

Well, it turns out that both humans and agents tend to accidentally do exactly that. For example:
- Let's say you have a `wasp start` process running.
- Then, in a different terminal, you accidentally call `wasp build`.

Older versions of Wasp didn't handle this conflict well. `wasp build` would either silently break something in the background or fail with a cryptic error that sends its reader, be it you or the agent, on a wild goose chase.

Wasp 0.26.0 still has the same constraint, that only one of these commands run at any given time, but it handles the situation more gracefully.
The error now features a nice explanation together with the PID of the already running process:

```
$ wasp build
❌ --- [Error] Wasp project is already in use: ------------------------------------

Another Wasp command (PID 3011345) is already running for this project. Stop it before running this command.
```

The agent can now immediately understand what's happening and decide what to do about it.

### Port conflicts between worktrees

Git worktrees are like local clones of a Wasp project, and they're great for isolation.
Setting up an agent to work in a worktree gives it:
- Its own copy of the code.
- Its own working directory for running commands.

That might seem like everything you need to let agents independently work on different things.

Well, not quite...

Wasp processes can still end up fighting over shared system resources, such as ports.
Let's see why that's a problem.

To run a Wasp app in development mode, you must usually use **two `wasp` commands** to start **three separate processes**:
- `wasp start db` starts a Postgres **database** in a Docker container, exposes a port on the host, and gives you a connection URL.
- `wasp start` starts a Node backend **server** and a Vite-based **client**.

Each worktree gets its own processes and its own database. No issues there.

But each process needs a port and, since the processes must to know where to reach each other, these ports must be decided ahead of time.
If Wasp dynamically picked an available port when starting up each process, the client wouldn't know where to find the server, the server wouldn't know where to find the database, and so on.

When you're only working on a single thing, predetermined fixed ports aren't a problem - the database always runs at `5432`, the client at `3000`, and the server at `3001`.

But what happens when you bring multiple agents into the picture, each with their own workspace? Well, that's where the trouble begins.

In previous version of Wasp, all three processes (client, server, database) always wanted to run on the same three ports, regardless of the worktree.
In practice, this meant that no two agents can have their dev servers running at the same time.

With Wasp 0.26.0, this is no longer the case. You can now have all the worktrees your heart desires, and run `wasp start` and `wasp start db` in each worktree with no interference.

## How did we fix it?

Conceptually, the solution is obvious - just get each process to dynamically choose an available port.

For example, when the agents run `wasp start db`:
- The first agent starts a database on `localhost:5432`.
- The second agent starts a database on `localhost:5433`.

The same applies to `wasp start`:
- The first agent starts the client at `localhost:3000` and the server at `localhost:3001`.
- The second agent starts the client at `localhost:3002` and the server at `localhost:3003`.

And that is exactly what Wasp now does.

It's a simple solution, but not an easy one.
As hinted earlier, the tricky part is communicating each chosen port to the other processes in the group, like telling the server where exactly to find the database.

There are quite a few ways to approach this and plenty of edge cases to consider. It's all interesting stuff, but out of scope for a feature announcement - you don't need to know any of the improvements' details to put them to use!

## How to use this?

There's nothing special you need to do!

Keep running `wasp start` and `wasp start db` as you've always done.
Wasp automatically takes care of all the port machinery under the hood:

```bash
# Starts the client and the server on the first two free ports it finds.
# It starts looking at 3000 and goes up.
wasp start

# Starts the dev database on the first free port it finds.
# It starts looking at 5432 and goes up.
wasp start db
```

Though there are two things to keep in mind.

First, your Wasp processes will no longer always run on the same port (i.e., `3000` for the client, `3001` for the server, and `5432` for the dev database).
They'll run on the first available port after those, so pay attention to where Wasp tells you they're listening.

And second, since you'll now be working in many worktrees, that also means you'll have many databases (remember, each worktree gets its own database).
Database are not terribly useful without data, so you might want explore how to [seed them](/docs/data-model/databases#seeding-the-database).

### Bonus feature

As a bonus, Wasp 0.26.0 allows you to specify the exact ports you want Wasp to use for your client and your server.
These flags work for both `wasp start` and `wasp build start`:

```bash
wasp start --client-port 4000 --server-port 5000
wasp build start --client-port 4000 --server-port 5000
```

If any of those ports is taken, Wasp will fail instead of looking for alternatives.
It concludes that you care about your process running on those specific ports, so it's better to explicitly fail than silently start listening elsewhere.
It's up to you to either free those ports up, specify different ports, or remove the port arguments.

## Try it out

Parallel worktree support is live in Wasp 0.26. If you're not on it yet, update your Wasp CLI:

```bash
npm i -g @wasp.sh/wasp-cli
```

Since Wasp now manages the ports and URLs in development, setting them yourself (e.g., `server.port` in `vite.config.ts` or `PORT` in `.env.server`) is now an error.
Check the [migration guide](/docs/migration-guide) for the full list of changes and how to update your project.
