Wasp 0.26 improves support for agent orchestrators and multiple Wasp project instances in Git worktrees:
- It's no longer possible to accidentally run incompatible Wasp commands at the
same time. For example, executing `wasp build` while `wasp start` is already
running won't corrupt the generated code.
- Wasp no longer runs into _"This port is already taken"_ errors when spinning up its dev servers.
Both `wasp start` and `wasp start db` now dynamically look for free ports.

## What are Git worktrees and why do agent orchestrators need them?

Before we dig into the new features, let's do a quick intro on what agent orchestrators and Git worktrees even are and why they're important.

If you know all about this, feel free to skip right to the [next section](#using-orchestrators-with-wasp). If not, here's a refresher:

- An **agent orchestrator** is a tool for coordinating agents. It helps you assign tasks to agents and keep track of their work, without juggling thirteen terminal windows and losing your mind. Examples of popular agent orchestrators are [Herdr](https://github.com/herdrdev/herdr), [Workmux](https://github.com/raine/workmux), and [Conductor](https://www.conductor.build/).
- **[Git worktrees](https://git-scm.com/docs/git-worktree)** are a Git feature that lets you check out multiple branches of a Git project at the same time, each one in its own isolated directory.

Developers use agent orchestrators to work on several features simultaneoulsy:
1. The orchestrator gives each agent an isolated Git worktree. The agent works inside it and does whatever it needs.
2. While the agents do their thing, the orchestrator lets you know each time one of them needs your input.
3. When a feature is done, you review the diff and use the orchestrator to merge it into `main`, deleting the worktree.

## What's new in Wasp?

Wasp used to have poor support for orchestrator workflows. You technicaly _could_ set them up, but it was a whole ordeal.

The technical dtails are interesting but a story for another time. All you need to know now is:
- Different Wasp commands in the same project no longer overwrite each other's outputs.
- Wasp commands across different projects no longer compete for the same TCP ports.

## How to use this?

There's nothing special you need to do!
Just keep running Wasp commands as you've always done.

### Wasp commands no longer fight over the file system 

Before Wasp 0.26, running multiple Wasp commands in the same project could cause them to write over each other's outputs.
For example, executing `wasp build` would break an already running instance of `wasp start`.

Wasp 0.26 prevents such conflicts:

### Wasp projects no longer fight over ports

Before Wasp 0.26, it was problematic to run `wasp start` and `wasp start db` in multiple worktrees:
all clients would fight over port 3000, servers over 3001, and databases over 5432. This lead to many _"Port already taken"_ errors.

Wasp 0.26 solves this problem with dynamic port allocation.

If you have a bespoke system for handling port conflicts, it's finally time to retire it.
Just run the commands you want to run, and Wasp takes care of the rest:

```bash
# Starts the client and the server on the first two free ports it finds.
# It starts looking at 3000 and goes up.
wasp start

# Starts the dev database on the first free port it finds.
# It starts looking at 5432 and goes up.
wasp start db
```

That said, there are two things to keep in mind.

First, your Wasp processes will no longer always run on the same ports (i.e., `3000` for the client, `3001` for the server, and `5432` for the dev database).
They'll run on the first available ports starting from those, so pay attention to where Wasp tells you they're listening.

Second, since each worktree gets its own database, working in many worktrees means having many databases.
Databases are not terribly useful without data, so we recommend you [seed them](/docs/data-model/databases#seeding-the-database).

:::caution Breaking change
Because Wasp now manages the ports and URLs in development, setting them yourself (e.g., `server.port` in `vite.config.ts` or `PORT` in `.env.server`) is an error.
Check the [migration guide](/docs/migration-guide) for the full list of changes and how to update your project.
:::

### Bonus feature

Wasp 0.26 allows you to specify the exact ports you want Wasp to use for your client, your server, and your dev database.
The client and server flags work for both `wasp start` and `wasp build start`:

```bash
wasp start --client-port 4000 --server-port 5000
wasp build start --client-port 4000 --server-port 5000
wasp start db --db-port 6000
```

If any of those ports is taken, Wasp will fail instead of looking for alternatives.
The reasoning is that you care about your process running on those specific ports, so it's better to explicitly fail than silently start listening elsewhere.
It's therefore up to you to either free those ports up, specify different ports, or remove the port arguments.

The `--db-port` flag was contributed by [Nihal Ahamed](https://github.com/Nihal-Ahamed-MS).
Thanks for all the patience during the design changes and reviews, Nihal!

## Try it out

Parallel worktree support is live in Wasp 0.26. If you're not on it yet, update your Wasp CLI:

```bash
npm i -g @wasp.sh/wasp-cli
```

If you haven't set up worktrees for your Wasp project yet, the [Git worktree setup](/docs/wasp-ai/git-worktrees) guide walks you through it.
