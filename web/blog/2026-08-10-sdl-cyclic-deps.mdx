Have you ever wondered why different frameworks have different approaches?
One framework seems to connect everything magically, while the other one forces you to do the work yourself.

But, that degree of magic you feel when working with some framework is not some ideal every tool should persuade, it’s a tradeoff.
Magic *can* feel **good as DX**, but it **requires harness** to work.

### tRPC

Let’s start with a "less magical" experience, a library called tRPC.

1. We start by initializing the tRPC, which gives us access to our router.

    ```tsx title="src/server/trpc.ts"
    import { initTRPC } from '@trpc/server';

    const t = initTRPC.create();
     
    export const router = t.router;
    export const publicProcedure = t.procedure;
    ```

2. After defining our operations, **we** (the people) have to collect all of them into our `router` constructor. 
   A single intialization point is necessary for proper type infererence.

    ```tsx title="src/server/appRouter.ts"
    import { router } from "./trpc";
    import { userGetAll } from "./users";
    import { taskGetAll, taskCreate } from "./tasks";
     
    export const appRouter = router({
      userGetAll,
      taskGetAll,
      taskCreate,
    });
     
    export type AppRouter = typeof appRouter;
    ```

3. To use the type-safe client, **we** have to create it. 
   The type-safety comes from passing the server router type to the client.
   Importing a server module from the client is fine here, since once compiled, this import will not exist.

    ```tsx title="src/client/index.ts"
    import { createTRPCClient, httpBatchLink } from '@trpc/client';
    import type { AppRouter } from '../server/appRouter';

    export const trpc = createTRPCClient<AppRouter>({
      links: [
        httpBatchLink({
          url: 'http://localhost:3000',
        }),
      ],
    });
    ```

4. Finally, we can use our operation by calling it through the client we created. 

    ```tsx title="src/client/someFile.ts(x)"
    import { trpc } from "./index";

    const users = await trpc.userGetAll.query();
    ```

We can see that tRPC only helped with the initialization of the client and the router. The rest is on the user.

If we give it a thought, **it’s easy to understand the TypeScript background following the workflow**.
We can guess it uses generics to ensure the the type safety. It's easy to track the flow of values and types.

### Wasp

And now, for something a bit more magical, let’s take see how Wasp works:

1. Before defining our operations, we specify them in the [Wasp Spec](/blog/2026/06/15/wasp-typescript-spec).
   This gives all the necessary information Wasp needs for operations.
   It also generates the operations types for type-safe definitions (e.g., provides related entities as params).

    ```tsx title="main.wasp.ts"
    import { app, page, route, action, query } from "@wasp.sh/spec";

    import { LandingPage } from "./src/LandingPage" with { type: "ref" };
    import { userGetAll } from "./src/user/operations" with { type: "ref" };
    import { taskGetAll, taskCreate } from "./src/task/operations" with { type: "ref" };

    export default app({
      // ...
      spec: [
        // ...
        query(userGetAll, { entities: ["User"] }),
        query(taskGetAll, { entities: ["Task"] }),
        action(taskCreate, { entities: ["Task"] }),
      ],
    });
    ```

2. After we’ve defined our operations, Wasp exports the type-safe client. We can use our operation by importing it.

    ```tsx title="src/user/someFile.ts(x)"
    import { userGetAll } from "wasp/client/operations";

    const users = await userGetAll();
    ```

Okay, albeit more stuff is hidden in the framework, on first thought, everything also seems sound here.
Wasp locates the operations through `spec`, where it can find all of the information to generate a client for you.

## Cyclic dependencies in TypeScript

Aren't cyclic dependencies allowed in TypeScript?

We need to be aware of the distinction of cyclic dependencies between TypeScript modules (inside the same TypeScript project) and TypeScript projects.

When importing in context of a single TypeScript project, cyclic imports are allowed.
The problem is when you import between TypeScript projects, where the [dependency graph must be acyclical](https://github.com/microsoft/TypeScript/issues/33685) (DAG).

<ImgWithCaption
  source="img/blog/sdk-cyclic-deps/typescript-cyclic-imports.png"

The SDK and the user project are two different TypeScript projects. So it is illegal.

### Solving cyclic dependencies between TypeScript projects

How does one usually solve cyclic dependencies?

Well, if you have cyclic deps between TypeScript projects, that is usually a sign of:
1. Bad code placement.
2. You actually don’t have two difference TypeScript projects. You have a single TypeScript project that was mistakenly split into two.

It this bad code placement? I mean, not really. If we move most of the logic to the user project, we will end up with tRPC, which is not what we are aiming for.

We also can't combine the projects. SDK is something which we must provide to users as a standalone package.

And even if do try to combine the projects, we encounter problems.
Since it is a single TypeScript project, both the SDK and the user project will follow the same compilation rules.
Either our SDK is at mercy of user (which is a no go), or the user is not in control of it’s `tsconfig.json`.
It can work, but it’s bad DX.

So, it’s just impossible. **SDK can never have a dependency on the user project**. 

The solution is not in project dependencies. But still, it is the behavior we want emulate. 
It is the both the perfect solution, and impossible solution for us. 
We must achieve the same behavior, but without dependencies.

## Emulating TypeScript project dependencies behavior

Since the SDK can’t have a TypeScript project dependency on the user project, let’s emulate it!
What do project dependencies even enable us?

Well, we can:

1. **Import types from the dependency**.

   E.g. SDK imports user operation definition type to create a client for that operation. We do it to extract operation inputs/outputs.

2. **Import values form the dependency**.

   E.g. The operation client must actually call the operation that user defined. So we must have a reference to that value (operation definition).

### Pushing types from the user project to the SDK

So, how to push user types form the user project to the SDK?
TypeScript provides functionalities out of box that allow that. 
You’ve probably used that feature yourself, without even knowing what you are doing.

Maybe you wanted `tanstack-query` to use your custom error by default?
In that case you copied [something like this](https://tanstack.com/query/latest/docs/framework/react/typescript#registering-a-global-error) in your project:

```tsx
import '@tanstack/react-query'

declare module '@tanstack/react-query' {
  interface Register {
    defaultError: MyCustomError
  }
}
```

This is the same trick that we are going to use to ensure type safety.

It lives on two separate TypeScript concepts working together: 
1. **[Interface declaration merging](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#merging-interfaces)** 
2. **[Module augmentation](https://www.typescriptlang.org/docs/handbook/declaration-merging.html#module-augmentation)** (not to be confused with [module declaration](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html), which is a similar but separate concept).

#### Interface declaration merging

In general, “declaration merging” means that the TypeScript compiler merges two separate declarations declared with the same name into a single definition. 
This merged definition has the features of both of the original declarations.

```tsx
interface Box { height: number; }
interface Box { width: number; }

const pass: Box = { height: 5, width: 6 }; // ok
const fail: Box = { height: 5 };
//    ^!: Property 'width' is missing in type '{ height: number; }'
//        but required in type 'Box'.(2741)
```

This works on all names in the same **declaration space**.
 Previous example declared the same interface in the same module, so they merged.

But if we e.g. defined them in separate modules, they would keep stay separated.
In fact, importing the same-named interface from one module to another would throw an error.

```ts title="a.ts"
export interface Box { height: number };
```

```ts title="b.ts"
import { Box } from './a';
interface Box { width: number }
//        ^!: Import declaration conflicts with local declaration of 'Box'.(2440)
```

#### Module augmentation

Module augmentation allows us to to augment (modify in a way which expands) existing modules.
The target module is specified the same as in `import/export` syntax.

How we can modify them is implied by “augmentation” in the name.
You are not allowed to declare new top-level declarations, you can only patch existing ones. 
And only named exports are allowed (because `default` is a reserved keyword).

```ts title="a.ts"
export interface Box { height: number; };
```

```ts title="b.ts"
import { Box } from './a';

declare module './a' {
  interface Box { width: number; } // ok
}

const pass: Box = { height: 1, width: 2 }; // ok
```

#### How we use it in the SDK

So the whole idea was for the the user project to push types into the SDK. 
So let’s show an actual example how Wasp does it:

{/* TODO: link to github files once merged */}

1. The SDK defines an empty `Register` interface (name by convention). 
   This interface must be a part of the public API, otherwise the user project can’t augment it.
    
    ```ts title="sdk/wasp/types/register.ts"
    export interface Register {}
    ```
    
2. In a file which is part of user’s project (we made it so in their `tsconfig` file):
    
    ```ts title="tsconfig.src.json" ".wasp/out/types/app"
    {
      // ...
      "include": ["src", ".wasp/out/types/app"],
      // ...
    }
    ```
    
    We generate a module thats augments the SDK's `Register` interface:
    
    ```ts title=".wasp/out/types/app/sdk/register.ts"
    import "wasp/types"
    
    declare module "wasp/types" {
      interface Register {
        prismaSetupFn: typeof import('../../../../../src/features/db/prisma').setUpPrisma
        serverEnvValidationSchema: typeof import('../../../../../src/env').serverEnvValidationSchema
        clientEnvValidationSchema: typeof import('../../../../../src/env').clientEnvValidationSchema
        operations: {
          'getTasks': typeof import('../../../../../src/features/operations/queries').getTasks
          // ...
        }
      }
    }
    ```
    This "pushes" types of user defined code to the SDK.
    
3. The SDK dervies all the user-code dependent types from the `Register` interface.
   We check if a value exists for the specified key, and if it does, we use it.
   If not, we falls back to our default value.
    
    ```ts title="sdk/wasp/types/register.ts"
    /** 
     * Safely reads values from {@link Register}.
     * Returns the registered type for a given {@link Key}, or falls back to {@link Fallback}.
     */
    export type FromRegister<Key extends string, Fallback> = Key extends keyof Register
      ? Register[Key]
      : Fallback;
    ```
    
    This fallback is really important. As previously mentioned, the SDK is compiled independently.
    That means, that even without any module augmentation, the SDK still must be valid TypeScript project.
    The default value must satisfy all the constraints that we expect of some type.
    
    E.g. for `serverEnvValidationSchema`, if user didn’t specify anything, we default to a empty `zod` object schema: 
    
    ```ts title="sdk/wasp/server/env.ts"
    export type RegisteredServerEnvValidationSchema = FromRegister<
      "serverEnvValidationSchema",
      z.ZodObject<{}>
    >;
    ```
    Since the server env validation code excepts “any” `zod` schema, this is enough for TypeScript to compile.
    
    Same pattern is applied for any SDK code that depends on the user project types.
    
Seems easy enough. But there is still one last catch. Emitted declaration files.

#### Forcing the conditional types to survive

The whole approach depends on `FromRegister` staying a conditional type.
And TypeScript really does not want to keep it that way.

Remember, the SDK is a standalone project, it compiles alone.
Module augmentation is not a part of the SDK compilation.
So, whenever the compiler sees `FromRegister<"someKey", Fallback>`, it resolves it on the spot.
`Register` is always empty,so  the whole conditional collapses to `Fallback`. No need for complexity.

While that alone is fine (the SDK still compiles), the problem is how the user project seessees the SDK.
In emitted `.d.ts` files, for every value whose type is *inferred*, TypeScript emits the *resolved* type.

Consider the following code (`Schema` is a minimal `zod` stand-in, to keep the compiled output readable):

```ts title="sdk/wasp/server/env.ts (simplified)"
// The env vars Wasp itself needs.
const waspServerEnvSchema = makeSchema<{ PORT: number }>();

declare function getUserSchema<Key extends string, Fallback>(
  key: Key,
  fallback: Fallback,
): FromRegister<Key, Fallback>;

// Everything below is inferred. No explicit type annotations.
const userServerEnvSchema = getUserSchema("serverEnvValidationSchema", makeSchema<{}>());
const serverEnvSchema = intersectSchemas(userServerEnvSchema, waspServerEnvSchema);

export const env = serverEnvSchema.parse(process.env);
```

Here is the compiled declaration file. In full:

```ts title="sdk/wasp/server/env.d.ts (compiled, inferred)"
export declare const env: {
    PORT: number;
};
```

`FromRegister` left no trace. And that is a problem.
The user project will always see thee `Fallback`, even if it does module augmentation.
The conditional type is gone, so there is nothing left to react to the augmented `Register`.
The type can never switch to its "user derived type" variant. It's `Fallback`, forever.

How do we stop this? A compiler flag? Well, there is nothing like that.
We have to exploit that TypeScript only computes the types it has to infer.
**A type annotation you write out EXPLICITLY is copied into the declaration file verbatim**.
So we must explicitly set the conditional type on every type derived from the `Register`:

```ts title="sdk/wasp/server/env.ts (simplified)"
// This one can still be inferred, it comes from the SDK itself.
const waspServerEnvSchema = makeSchema<{ PORT: number }>();

// We must explicitly set the conditional type here.
type RegisteredServerEnvValidationSchema = FromRegister<
  "serverEnvValidationSchema",
  Schema<{}>
>;
type UserServerEnvSchema = RegisteredServerEnvValidationSchema;
const userServerEnvSchema: UserServerEnvSchema = makeSchema<{}>();

// We must explicitly set the type here.
type CompleteServerEnvSchema = SchemaIntersection<UserServerEnvSchema, typeof waspServerEnvSchema>;
const serverEnvSchema: CompleteServerEnvSchema = intersectSchemas(
  userServerEnvSchema,
  waspServerEnvSchema,
);

// We must explicitly set the type here.
export const env: Infer<CompleteServerEnvSchema> = serverEnvSchema.parse(process.env);
```

And now the compiled declaration file keeps everything:

```ts title="sdk/wasp/server/env.d.ts (compiled, explicit)"
import { FromRegister } from "../types/register.js";
import { Infer, Schema, SchemaIntersection } from "shema-package";
declare const waspServerEnvSchema: Schema<{
    PORT: number;
}>;
type RegisteredServerEnvValidationSchema = FromRegister<"serverEnvValidationSchema", Schema<{}>>;
type UserServerEnvSchema = RegisteredServerEnvValidationSchema;
type CompleteServerEnvSchema = SchemaIntersection<UserServerEnvSchema, typeof waspServerEnvSchema>;
export declare const env: Infer<CompleteServerEnvSchema>;
export {};
```

The conditional type survives, written out exactly as we wrote it.

Yep, a lot of forced types, but that is the whole trick.
You can get away with this approach as long as every type derived from the `Register` is set explicitly, be it `: RegisteredType`, `as RegisteredType` or `T extends RegisteredType`. 

### Pushing values from the user project to the SDK

So the SDK must accept values from a consumer.
And what it can accept is defined by a contract / interface.
This is usually known as dependency inversion.

#### The staightforward approach

A staightforward way to implement this would be to use dependency injection.
You export a function to “register” external dependencies, and your SDK handles logic depending if the dependencies had been registered.

Suppose a full-stack framework’s dependency graph looks like this:

<ImgWithCaption
  source="img/blog/sdk-cyclic-deps/full-stack-app-deps.png"
  alt="TODO"
/>

The SDK depends on nothing, the user project depends on the SDK, and the generated client and server depend on both the user project and the SDK.

Either the user can do it manually (but we don’t want that) or we can do it for user in the generated client and server projects.
This also creates a nice runtime split, e.g. for operations, the generated server project would register the user’s operations into the SDK.

Though, one big problem of this approach is race conditions.
The dependencies must be registered before they are used for the first time.
This requires precise balancing of module initializaiton order, which is a chore.
I’d be best if we could avoid it.

#### The proxy approach

One thing to remember is that cyclic dependencies are a problem only in TypeScript projects. 
JavaScript itself has no problems with cyclic imports between modules. Aa long as we don’t have cyclic value initialization.

And in the end, the code will be nothing but bunch of javascript bundles in the end. The server bundle will be mix of original server code, SDK code and user project code. Can we somehow, in e.g. server, use a variable from the user project it will have in server bundle, but without strictly depending on the user project? Well, yes we can! 

This is the problem that virtual modules can solve.
We will create a module under a name, e.g. `virutal:wasp/user/action/userGetAll`. And we will import user variables form it, e.g. `import { userGetAll } from "virutal:wasp/user/action/userGetAll"`, all while excepting that this magical name gets resolved to the actual user file where the operation is defined during bundle time. 

And it works like this:

```tsx
/**
 * Maps the name of a virtual module pointing to the user's file to
 * that file's relative import path from the server project root.
 * 
 * @example serverUserVirtualModuleMap["virtual:wasp/user/server-env-schema"] // resolves to "../../../src/env"
 */
const serverUserVirtualModuleMap: { [userVirtualModuleId: string]: string } =  {
  // ...
};

/**
 * Resolves virtual modules pointing to user's files.
 * User virtual modules allow Wasp code to depend on user code at runtime,
 * without depending on the user's project during TypeScript compile time.
 */
export function userVirtualModules() {
  return {
    name: "wasp:user-virtual-modules",
    async resolveId(id) {
      if (id in serverUserVirtualModuleMap) {
        const absPath = path.resolve(serverRootDir, serverUserVirtualModuleMap[id]);
        return await this.resolve(absPath, undefined, { skipSelf: true });
      }
      return null;
    },
  };
}

```

So for each time we encounter virtual modules pointing to user’s files, we just resolve them to user’s files. That’s it.

Only detail left to do is to make this compilable in TypeScript.
Since we import from “non-existant” module, we need to either ignore the type error, or declare module type declarations.

```tsx
// @ts-expect-error
import { customSignup as customSignup_ext } from 'virtual:wasp/user/action/customSignup'

// or

declare module "virtual:wasp/user/action/customSignup" {
  import { RegisteredCustomSignup } from "./server/operations/actions/index";

  export const customSignup: RegisteredCustomSignup;
}
```
